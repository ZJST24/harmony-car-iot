1总体：这个项目在干嘛

一句话：让一块屏幕（手机）能看见一辆小车在哪、并指挥它往哪开；而中间所有和云打交道的麻烦事，都交给一个自己写的后端去挡。

为什么要分五层：如果让手机 App 直接连华为云，就得把云的密钥（AK/SK）塞进 App 包里 —— 谁都能反编译拿出来，等于把银行卡和密码一起发出去。所以中间插一个后端当"前台"：App 只跟后端说人话（HTTP），后端再拿着钥匙去跟云打交道。

① 鸿蒙 APP
手机上的界面 · 不持有任何云凭证
⑤ 网页视图
浏览器里的控制台 / 俯视图
HTTP / JSON · 轮询 2 秒 · 命令同步
② 业务后端（Python + Flask）
唯一持有 AK/SK 的地方 · 命令白名单 · 审计日志 · :8000
HTTPS OpenAPI · 每次请求都要签名
③ 华为云 IoTDA（物联网平台）
实例 9f149bee02 / cn-north-4 · 设备影子 · 物模型
MQTTS / TLS 8883 · 一机一密
④ 模拟小车（Python 脚本，不是真车）
本质就是一个 MQTT 客户端 · 自己算位置 · 定时上报

三个最容易误解的地方

以为实际为什么重要
"小车是硬件，我用代码控制它" 小车是 car_mqtt_client_001.py 这个 Python 脚本，位置是它自己用数学算出来的（x += sin(heading) × 速度 那类） 搞清这点，你才知道"为什么改代码能让车动"
"App 打开就能看到实时位置" App 看到的是云端的设备影子（一块黑板），影子由小车定时写（动时 5 秒、停时 60 秒） 这解释了"为什么画面会跳、为什么车停着数字不动"
"云端会主动推消息给 App" 不会。App 每 2 秒问一次后端"现在怎么样"（轮询），后端每次去云上读两次 这决定了免费额度、延迟、以及为什么后端调用次数是 App 的两倍

3线：4 条主线

面是"知识分类"，线是"数据实际怎么跑"。项目里所有代码，都能挂到这 4 条线上的某一环。

下行线 1 · 控制：点一下按钮，车开始动
  1. 点按钮 APP 或网页触发，所有按钮立即变灰禁用（防止连点把额度刷爆）
  2. POST /command 请求体 {"cmd":"FORWARD","speed":60}，后端先过白名单
  3. 构造云请求 后端拿 AK/SK 签名，调 CreateCommand，service_id 写死 car
  4. 云下发 云端查物模型确认这条命令存在，再通过 MQTT 主题推给设备
  5. 车执行 脚本收到消息，改自己的速度/朝向，然后立即回执
  6. 回执回流 回执沿原路返回，后端看到 response_name 有值，才敢说 executed:true
  7. 界面反馈 显示"✓ FORWARD 已执行（383 ms）"，同时命令写进 commands.log
涉及的点：C3C5C7B3B6A1A5D4
上行线 2 · 观测：屏幕上的车为什么在那儿
  1. 车自己走 脚本按速度每 100ms 推进坐标（没有人告诉它"你现在在哪"）
  2. 定时上报 运动中 5 秒一帧、静止 60 秒一帧，把 5 个属性发给云
  3. 云写入影子 平台把这份数据存成"最新状态"，并记下事件时间
  4. App 轮询 每 2 秒 GET /status，后端这一下要打两次云 API（读影子 + 查在线状态）
  5. 画布外推 两次上报之间，App 自己按速度往前猜位置（航位推算），新数据到了再校正
  6. 白圈校正 那个白圈就是"真实上报点"，车漂到哪儿都会被拉回来
涉及的点：B4B5C4C6D5E3
接入线 3 · 设备上线：脚本是怎么"登"上云的
  1. 算密码 拿设备密钥（secret）和时间戳做 HMAC-SHA256，得到这一次连接的密码
  2. 拼身份 clientId = 设备ID_0_1_时间戳，username = 设备ID
  3. TLS 连接 连 8883 端口，云端校验密码对不对（错了就是 rc=4）
  4. 订阅主题 订阅自己的命令通道，之后云端推的命令才收得到
  5. 补一帧 立刻上报一次属性，控制台里设备状态从离线变 ONLINE
涉及的点：A2A3A4A5A6E1
凭证线 4 · 后端凭什么能调云：签名的三个条件
  1. 身份三件套 AK（你是谁）、SK（你的章）、project_id（在哪个项目/区域干活）
  2. 专用地址 必须用实例专属域名，不能用通用域名，否则恒定 403
  3. 衍生签名 每次请求临时算一个签名，而不是把 SK 直接发出去
  4. 别多传参数 请求里再带 instance_id 反而报错（域名里已经含了）
  5. 报错识别 这三项任一出错都是 403 IOTDA.000021，而且文案会误导你去查权限
涉及的点：B7B8B1C5C6E5
怎么用这 4 条线自测：随便挑一条，合上文档，从第一环讲到最后一环。卡在哪一环，就去补那一环对应的"点"。

5推荐学习顺序

下面的顺序是按依赖关系排的：每一步都用得上前一步的东西。不必严格照做，但跳步容易卡住。

0
先让项目跑起来（约 1 小时）
三个进程：车端脚本、后端、App/网页。跑通一次，再开始拆。这一步只看 项目交接.md 第 4 节。
学完能回答：我改完代码要重启哪个进程？
1
面 C · 后端（最先看，因为它是全链路的枢纽）
重点：一个请求怎么进来、怎么变成一次云调用、怎么变成一段 JSON 回去。把 app.py 的 200 行按三个接口读完。
学完能回答：curl /command 之后，代码依次执行了哪几行？
2
面 B · 云平台概念（理解后端在"跟谁说话"）
重点：物模型、设备影子、属性/命令的区别。不用记控制台每个按钮，只要知道这三样是什么、谁写的、谁读的。
学完能回答：为什么设备离线后，/status 还能返回一组坐标？
3
面 A · MQTT（设备侧到底怎么连的）
重点：主题、订阅、一机一密。可以边看边故意把时间戳改成北京时间，观察 rc=4，比看十遍文档印象深。
学完能回答：为什么两台脚本连同一个设备会互相踢下线？
4
面 D · 鸿蒙应用（最独立，可以放最后）
重点：状态驱动刷新（D3）+ 发请求（D4）。界面部分不用背属性名，用 DevEco 的预览器边改边看最快。
学完能回答：为什么指标曾显示 --，改成组件后就正常了？
5
回头看细节 · 点（按需挑）
这时候你已经有了骨架，剩下的点会自己"挂"上去。建议从 36 个点里挑 6 个高性价比的深挖，而不是全刷一遍。
提示：学完每一条，回来在这张图上打个勾，进度会更清楚。
